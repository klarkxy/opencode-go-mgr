# Runtime Invariants

Behavioral invariants of the running system. Read this before changing gateway routing, aliases, Zen Free, the plan catalog, access keys, outbound proxy, or usage sync. Code is the source of truth; this page maps semantics that are easy to get wrong.

## Gateway And Model Lists

- Core Gateway: Axum + Tokio + reqwest. The same port exposes OpenAI Chat Completions / Responses, Anthropic Messages, Gemini `generateContent` client entrypoints, and Claude Desktop alias entrypoints.
- Authenticated `GET /v1/models` lists currently-routeable Aliases authorized by the original static OpenCode Go protocol table plus the sealed MiniMax CN, Kimi CN, and selected GOAT long-name maps, then merges model IDs declared by eligible Custom accounts (enabled+ready+non-empty Key; verification is optional). Saved Zen rows may join Go-authorized Aliases; saved Command rows may join any code-owned Alias; saved MiniMax/Kimi rows activate only exact code-owned CN mappings. Unmatched built-in rows remain exact raw pins and are not advertised as new Aliases. Protected `GET /dashboard/api/v3/application-models` is **Go-routable Aliases ∩ current pricing snapshot** (highspeed inherits base-price rows; empty intersection is `[]`), excluding Custom and the CN Plans. Neither GET path makes upstream requests; catalog refreshes are explicit control-plane actions. Custom IDs come from eligible accounts' declared capabilities. Unknown model names return `400` on all supported client formats.
- Phase-one Custom mapping refinement: an eligible Custom capability has a public model name and an exact `upstream_model`. `/v1/models` publishes only the routeable public name, never a second upstream-ID catalog. Discovery yields upstream IDs and imports `public_model = upstream_model` exactly; it performs no suffix stripping or Alias synthesis. Raw conflicts are excluded from publication and resolve fail-closed as `ambiguous_model_id`. The separate Aliases page is a read-only aggregation of existing contracts and capabilities, not an Alias API, store, cache, or authoring surface.
- Gemini clients use `/v1beta/models/{model}:generateContent` or `:streamGenerateContent` (`/v1/models/...` also accepted), may auth with `x-goog-api-key`; Gemini is only a client format, and Gateway always converts to the known model's recommended upstream protocol. Unknown model names return `400` on Chat / Responses / Messages / Gemini; probing protocols is prohibited.
- Development-time protocol defaults are hard-coded in `ocg_domain::protocol::MODEL_PROTOCOLS` (`ocg-core` `kernel/protocol.rs` and `gateway/protocol.rs` are facade/host conversions): both `preferred` and `supported` reflect the official model endpoint documented when the release was developed. A client wire passes through only when it matches that official default or later persisted positive probe evidence; otherwise the request converts to the effective preferred protocol. Runtime request paths never probe. Explicit Provider probes may add positive evidence only inside the adapter's documented, constructible ceiling. Unknown future Zen Free rows remain off until a later code baseline or an explicit successful probe classifies them. The whole-document JSON conversion kernel is in `ocg-gateway`.

One logical client request captures `RequestSnapshots` at entry (`crates/ocg-core/src/gateway/executor.rs`). Fallback iterations re-read live account state; they do not recapture the frozen row. There is no extra snapshot service or trait.

| Frozen at entry | Re-read each fallback iteration |
| --- | --- |
| `AppConfig` | accounts |
| pricing snapshot | eligible Custom runtimes |
| `ForwardRouteSet` | Zen Free cooldown |
| provider contracts | current account availability |
| resolved Alias / raw identity | — |

## Dashboard V3 And V2 Tombstones

- Dashboard V3 is mounted at `/dashboard/api/v3`. Control-plane changes require CAS (`expectedRevision`, `processGeneration`; price writes also need `expectedPricingRevision`). `ConnectionInfo` is the only V3 response DTO allowed to return the plaintext Key; Key-mutation responses do not include plaintext, and the client re-fetches `GET /connection`. `GET /contract` returns the current process's live revision / generation token, not a contract-export endpoint.
- Node migration is V3-only at `POST /accounts/transfer/export|preview|import` and loopback-dashboard-only; forwarded scheme headers never grant access. Export has no administrator step-up. The dashboard receives a version-1 Argon2id (64 MiB, 3 iterations, one lane) plus AES-256-GCM envelope with fixed AAD, never plaintext account or Access Keys. Password work is process-wide single-flight and runs outside settings/SQLite locks; every response is `Cache-Control: no-store`. Preview and import share decrypt/validation, and legacy payload V1 remains readable. Import rechecks CAS after KDF and writes the database-owned merge in one SQLite transaction. Payload V2 established stable-ID identity: package fields win on matching account/Access-Key IDs; same Plan/name with different IDs coexist; existing destination account IDs keep their current order and source-only IDs append in package order. Destination-only Access Keys and Provider scopes remain. Different-ID Key value collisions, more than 64 active sub Keys, in-bundle duplicate IDs, or any invalid row reject and roll back the whole database merge. V2 carries usable ordinary accounts and verification state, ready account Keys, primary/active sub Access Keys, portable config, Zen Free state/catalog, and Provider catalogs/evidence/overrides. Matching destination rows retain local browser data plus usage/cooldown history; stale authentication and last-error flags clear with package-owned account credentials. Source browser profiles/cookies, login passwords, referral codes, logs, usage, cooldown state, and unfinished managed drafts are omitted. Destination listener/root URL and OS-owned auto-start/Dock settings remain local. All fallible runtime snapshot construction reads the uncommitted merged transaction; only after it succeeds does SQLite commit, followed by an infallible snapshot installation and one revision bump. V1 imports keep the old Plan/name duplicate-skip behavior.
- Current export refinement: the cryptographic envelope remains version 1, while newly exported portable content is payload V3. V3 carries Custom public-model → upstream-model mappings. Decrypt/validation continues to accept payload V1 and V2, treating their former single model ID as both identities.
- Legacy protected V2 REST (`/dashboard/api/...`, excluding V3) returns structured `410` (`code=dashboardV2Removed`) to authorized dashboard sessions; anonymous requests get `401` first. The following semantics are separate from this tombstone and must not be mixed up: V2/V3 auth and session, browser WebSocket, and inference entrypoints. The only preserved unversioned paths are exact `auth/status|register|login|logout` and `browser/sessions/{token}/ws`.
- `crates/ocg-core/src/dashboard.rs` now handles only SPA `index`/`assets` and preserved V2 auth and browser WS handlers; the tombstoned V2 REST middleware lives in `host_router.rs`. Provider model/protocol probing is the low-frequency V3 path `POST /providers/{provider_id}/protocol-probes`: it rejects models outside the effective Provider catalog, exposes no account selection, may walk routing-eligible accounts in saved order, and persists positive protocol evidence/`force_on`. The Accounts page uses the separate operational path `POST /accounts/{id}/model-tests` with only `{ modelId }`. It admits the model against that exact account's current scope, derives the effective protocol, and sends one minimal request through only that account. It has no CAS because it mutates no control-plane state; it never selects a sibling account, performs Gateway fallback, changes cooldown/verification/enablement, or writes Provider evidence. The dashboard sequences **Test all** client-side and keeps results only in the open dialog. Retired V2 account paths still return `410` after authorization; do not revive them.
- Request observability belongs exclusively to `forward_logs`: forwarded attempts, provider protocol probes, and authenticated local parse/validation/routing failures must not be duplicated into `gateway_logs`. Pre-selection failures use unresolved/Gateway attribution with zero token fields and `cost_state=not_applicable`. `gateway_logs` is reserved for operational lifecycle/control-plane events and failures to persist or finalize a request-log row. Unauthorized requests and expected local fallbacks remain unpersisted.

## Access Keys And Auth

- From schema v31 the authoritative table is SQLite `access_keys` (primary Key fixed id `gateway_keys::PRIMARY_KEY_ID` / `00000000-0000-0000-0000-000000000001`, name snapshot "Primary", never disable/delete; sub-Keys are non-primary rows, active limit 64, soft-delete keeps the name but clears plaintext). Sanitized config JSON stores `gateway_key` as `""` and is no longer DB-authoritative; in-process `AppConfig.gateway_key` and `GET /dashboard/api/v3/connection` still expose the live primary Key. Lifecycle is only through `/dashboard/api/v3/keys*` (including `POST /keys/primary/regenerate`). Primary/sub Key value mutual exclusion is enforced by `gateway_keys::ensure_primary_value_allowed`. `sub_gateway_keys` only appears in historical DBs before migration to v27 and is discarded after migration; do not describe it as the current authoritative table.
- Auth collects all non-empty candidate headers Bearer / x-api-key / x-goog-api-key; any match against the credential snapshot (`CoreStateInner.credential_snapshot`, including primary Key and enabled sub-Keys) passes, with attribution to the first match in candidate-header order; the same snapshot feeds the forward log name snapshot.
- Non-loopback listeners use single-admin login. Docker can be first-initialized via `OCG_ADMIN_USERNAME` and `OCG_ADMIN_PASSWORD` (both must be set together; setting only one causes a startup error); when not provided the first registered user becomes admin.

## Persistence

- Current schema is **v35**. v33 added non-null `account_model_capabilities.upstream_model` and backfilled it from `model_id`. v34 adds the singleton `cpa_integration` row; CPA inference credentials, enablement, and order remain on its reserved account, while its model snapshot stays in `provider_model_catalogs`. v35 creates `ollama_cloud_usage_state` (Ollama Cloud Cookie usage state; see `storage-migration.md`) Neither migration synthesizes Aliases. See `storage-migration.md`.
- SQLite migration history through **v32** remains in place: v27 copied the primary Key and `sub_gateway_keys` into `access_keys` and dropped the legacy five `usage_sync_*` columns on `accounts` (official usage-sync metadata is now in `provider_usage_sync_state`). v29 removed SCNet Token Plans and deleted existing SCNet account rows. v30 introduced the temporary Custom multi-protocol JSON set. v31 added `provider_contract_model_protocol_overrides` and stopped reading the `provider_contract_scopes` switch columns. v32 replaced each Custom row with `endpoint_url` plus one `upstream_protocol`; historical rows choose Chat, then Responses, then Messages, append the corresponding standard inference path, clear non-selected Custom protocol evidence/overrides/capabilities, and become disabled/pending. Existing non-empty DBs generate a non-overwriting `data.sqlite.pre-v3.<UTC>.bak` plus `.sha256` sidecar in the same directory before any migration write that crosses a major schema boundary; fresh empty DBs are created directly at the current schema without that copy. GUI data directory is Windows `%USERPROFILE%\.ocg-mgr` or macOS/Linux `~/.ocg-mgr`; CLI defaults to `~/.ocg-mgr-cli`. Upgrade, backup hashing, and failed-rollback are covered in `docs/maintainer/storage-migration.md`.
- Downstream access root URL priority: non-empty `OCG_CLIENT_ROOT_URL` > SQLite manual value > frontend auto-derived from production origin / dev Gateway port. Environment-variable overrides are read-only and must not be written back to SQLite.
- Desktop Gateway port priority: valid `OCG_GATEWAY_PORT` > SQLite `gateway_port` (default `9042`). The desktop Host and Vite development proxy read the same variable. The override is read-only, must not be written back to SQLite, and does not change CLI `serve --port` semantics.

## Desktop Host

- Tauri v2 cross-platform tray app; the main window is hidden by default; tray/single-instance logic opens `http://127.0.0.1:<port>/dashboard/` in the system browser, and loopback listeners skip login automatically. Host capabilities (gateway lifecycle, native browser, autostart, Dock, updater) are registered into `CoreState` and **not** registered as `#[tauri::command]` / `invoke_handler`. Do not describe "there are still live Tauri invoke commands" as the current state.
- The Settings page checks the latest GitHub Release via protected `GET /dashboard/api/v3/settings/check-update`. Installed desktop builds with the updater public key built in can download, verify the signature, and install in place; dev builds, CLI, Docker, and old versions not yet in the update channel keep the release-page / manual-overwrite path.

## Outbound Proxy

- Global outbound proxy is stored in `AppConfig`, with modes auto (system/environment), manual HTTP, force-direct, and per-model list (List). Non-List modes are mutually exclusive three-way; in List mode (`proxy_list_direction` allow/deny list + `proxy_list_models` known model ids), listed models take the direction exception segment (allowlist → proxy / denylist → direct), while unlisted models and non-model outbound (account test/verify, Zen Free manual model refresh, usage, pricing, updater download) take the direction default segment (allowlist → direct / denylist → proxy). List membership validation only runs at the dashboard `PUT /dashboard/api/v3/settings` write gate (non-empty, exact known ids, deduplicated); load paths tolerate stale values. Zen Free only hits the fixed `https://opencode.ai/zen/v1/models` when an admin explicitly refreshes, without a Key, not following redirects, and preserves the old snapshot if the refresh fails or returns empty. reqwest paths go through `ocg-core`'s `http_client.rs` facade into `ocg_infra::http`'s route set / `configured_builder`; the Tauri updater uses its `proxy` / `no_proxy` to align with the default segment and must not bypass per-account config. Forwarding picks routes from the request-entry snapshot; hot config switches do not affect in-flight requests. Custom HTTP (`custom.rs` + `custom_http.rs`, transport may reuse `ocg_infra::inference_http`) follows the same proxy policy; never follows redirects; never forwards dashboard/client auth; derives one auth header from the selected protocol (Bearer for Chat/Responses, `x-api-key` for Messages); and clamps timeout by `connect_timeout_secs` to 5–60 seconds.

## Plan Catalog And Custom API Boundary

- Plan catalog is in static `ocg_domain::provider::BUILTIN_PLANS`: OpenCode Go, Zen Free, Command Code GOAT, MiniMax CN Token Plan, Kimi Code CN, and Custom API. Internal identity is `provider_id` + `offering_id`. Command Code GOAT is routable and its public official `GET /models` is Provider catalog discovery, not stored-Key verification; historical GOAT verification states normalize to `not_required`, and inference 401/403 remains the actual Key-auth boundary. Accounts contribute enabled+ready+non-empty-Key credentials and ordering, while the Provider model/protocol contract owns model supply. The GOAT included-model preset defaults on; additional discovered rows default off and require an explicit `force_on`. There is no account-level GOAT/All or Max entitlement mode. A verified GOAT pricing snapshot supplies per-request price-and-multiplier accounting and never falls back to Go pricing. Command Code exposes no machine-readable account-usage endpoint, so GOAT usage availability is `local_state`, never authoritative: the dashboard projects priced OCG request logs into the public `$14 / $35 / $70` windows and permits manual baseline correction. Unpriced rows and traffic outside OCG are omitted; the estimate does not affect inference eligibility or start automatic sync. All persistence mutation paths still reject enabling any truly `routable=false` offering before write, revision, or timestamp changes; the desktop UI only mutates via Dashboard V3 HTTP and has no separate invoke mutation path.
- MiniMax (`minimax`/`cn`) and Kimi (`kimi`/`cn`) are separate sealed adapters, not Custom presets. Both use Bearer Keys, fixed no-redirect official origins, authenticated explicit `/models` refresh, generic provider cooldown on 429, and unpriced forwarding. Their official development-time ceiling is Chat Completions plus Anthropic Messages, with no Responses path. MiniMax Chat uses `https://api.minimaxi.com/v1/chat/completions` and Messages uses `https://api.minimaxi.com/anthropic/v1/messages`; Kimi uses `https://api.kimi.com/coding/v1/chat/completions` and `/v1/messages`. The MiniMax sealed map covers `MiniMax-M3`, M2.7/M2.5/M2.1 standard and highspeed variants, and `MiniMax-M2` with matching lowercase kebab Aliases. Kimi maps `kimi-for-coding` → `kimi-k2.7-code`, `kimi-for-coding-highspeed` → `kimi-k2.7-code-highspeed`, `k3` → `kimi-k3`, and `k3-256k` → `kimi-k3-256k`. Forwarding always preserves the exact upstream ID. MiniMax manually reads `https://api.minimaxi.com/v1/token_plan/remains`; Kimi manually reads `https://api.kimi.com/coding/v1/usages`. Bounded responses replace only the same account/provider source snapshot under V3 CAS. These windows are display-only: there is no automatic sync and they never affect inference eligibility. Other Kimi/GLM ordinary or private endpoints remain Custom API concerns; GLM has no built-in Plan.
- Custom API (`custom`/`api`, `routable=true`) is a trusted-admin destination with one HTTP/HTTPS API URL and one `chat_completions` / `responses` / `messages` protocol per account; valid new accounts default enabled. Embedded credentials, query, fragment, and redirects are rejected; dashboard/client auth is never forwarded. Chat/Responses construct only Bearer auth, Messages only `x-api-key`; there is no auth override or retry. A root URL resolves through `/v1` plus the selected protocol path; a base already ending in `/v1` does not duplicate the segment. Existing complete standard or non-standard Endpoints remain verbatim, with non-standard paths retaining manual model entry. The single protocol is uniform across every declared model and is the effective preferred protocol: matching client wire passes through; other supported client formats, including Gemini, convert to it. Custom config and the complete model-capability list replace atomically under one V3 CAS write. Model discovery uses `/v1/models` for root/versioned bases or the sibling `/models` for a standard complete Endpoint; it does not guess from non-standard complete paths. Custom per-model overrides may only target the account's declared protocol; `force_on` cannot expand beyond that declaration, while `force_off` makes the model unroutable with no fixed-order fallback. Eligible accounts (enabled+ready+non-empty Key) dynamically route their declared model IDs. Custom cost/usage is unpriced/unknown and does not deduct provider quotas. Multi-endpoint providers belong in a future static Provider Adapter, not this generic Custom route.
- Custom phase one keeps the Provider Registry static and sealed. Accounts is the sole mapping editor; it atomically stores one account-wide protocol with public-name → exact-upstream-ID rows. Aliases displays the read-only aggregate; its Custom edit deep link is `?view=accounts&account_id=<id>`. Closing clears `account_id`; a stale ID is noticed and cleared. No dynamic Provider, Alias registry, plugin point, runtime adapter loading, or request-time discovery is introduced.

## External Integrations

- External integrations are static product surfaces, not Provider/Plan plugins. CPA's implementation is currently staged for dedicated validation: its normal navigation entry is hidden, its catalog Plan is unroutable, and persistence clamps the singleton route account off. The typed V3 control plane remains available for isolated testing. OCG does not embed, start, upgrade, or read that service's private auth files.
- CPA accepts loopback origins on Desktop/CLI, or the fixed `http://cpa:8317` environment override in the sibling Compose profile. Redirects, embedded credentials, query/fragment URLs, remote/LAN hosts, and forwarding the client Key are forbidden. CPA inference is direct and isolated from the global outbound proxy.
- The reserved CPA account is a single route card in the ordinary account order and selector state machines. CPA's internal OAuth accounts are live projections only; logs attribute traffic to the CPA subscription pool, never a fabricated internal account. Management and Inference Keys stay encrypted locally, OAuth tokens remain in CPA, and node migration excludes all CPA-owned state.
- CPA catalogs may join only code-owned Aliases. Other saved IDs remain exact raw pins; conflicts fail closed. Known IDs use the OCG protocol table and unknown IDs default to Chat Completions without a billable probe. CPA costs and usage remain unpriced/unknown. Any CPA failure stays inside ordinary candidate fallback and must not impair existing routes.

## Aliases

- Client aliases live in `ocg_gateway::alias` (`ocg-core` `alias.rs` is the compatibility facade). Built-in Alias authority is code-owned: `ocg_domain::protocol::supported_model_ids()` supplies the original OpenCode Go namespace, while sealed exact maps supply MiniMax CN, Kimi CN, and selected GOAT long-name aliases without adding Go routes. Command first removes the Provider namespace and reuses an existing code-owned Alias; known plan suffixes such as `-paid` / `-free` are stripped only when the shorter name is already authorized. The sealed GOAT exception `nvidia/nemotron-3-ultra-550b-a55b` maps to `nemotron-3-ultra`; meaningful qualifiers such as `highspeed`, `vision-exp`, and `contributor` are not length-truncated. Saved MiniMax/Kimi catalogs activate only their sealed mappings. Unknown future rows stay exact raw pins until code assigns them an Alias. Alias spellings are case-folded; built-in raw IDs are exact and case-sensitive, including official mixed-case MiniMax IDs and IDs containing `/`, `_`, or whitespace. Custom declared IDs retain their existing case-folded matcher. A raw ID with exactly one registry mapping is pinned to that mapping before routability is checked; an unroutable mapping is recognized but cannot produce a production route. Overlapping exact raw IDs (including an eligible Custom declared ID conflicting with another Plan mapping) return `ambiguous_model_id` without calling upstream. A Zen Free `foo-free` row joins the suffix-stripped Alias `foo` only if `foo` is Go-authorized; the original `foo-free` remains an exact raw pin. Shared authorized aliases pick among Go/Zen/Command/MiniMax/Kimi/Ollama candidates in account-card persistence order. Ollama Cloud never creates or steals an Alias: a refreshed catalog may append one routeable Ollama mapping to a Go-owned alias only when stripping the `:` tag leaves exactly one catalog match (administrator matrix pins break rotation ties and are respected by later refreshes); date-tagged snapshot ids are runtime catalog data and must never be hardcoded. Eligible Custom declared IDs overlay into resolution and `/v1/models`, but must not steal already-published aliases. `/v1/models` publishes an Alias only while its exact saved catalog row exists and at least one mapping has an enabled effective protocol; all-off Provider scopes contribute no route. Forward logs distinguish `requested_model`, `resolved_alias`, and `upstream_model`; `native_cost_*` is optional; do not invent a `requested_alias` field. Claude Desktop's three role aliases are still rewritten before alias resolution; `/claude-desktop/v1/models` only publishes those three roles.

| Decision | Result |
| --- | --- |
| Code-owned kebab Alias | Resolves as Alias; published while a saved catalog row exists and at least one mapping has an enabled effective protocol |
| Unique raw ID | Pins to that mapping before routability is checked; unrouteable mappings are recognized but unpublished |
| Overlapping exact raw IDs | `400` `ambiguous_model_id`; no upstream |
| Zen `foo-free` | Exact raw pin always; joins Alias `foo` only when `foo` is Go-authorized |
| GOAT long name / suffix | Namespace stripped; `-paid`/`-free` stripped only if the short name is already authorized; `nvidia/nemotron-3-ultra-550b-a55b` → `nemotron-3-ultra` |
| MiniMax / Kimi sealed map | Saved catalog activates only code-owned mappings; unmatched rows stay exact raw pins |
| Eligible Custom declared ID | Overlays resolution and `/v1/models`; must not steal a published Alias |
| `/v1/models` publish gate | Exact saved catalog row + at least one enabled effective protocol; all-off scopes contribute no route |

## Zen Free

- Zen Free is a special built-in account without a Key; it only has an account-card enable switch, and no longer has `deny` / `explicit` / `prefer` or auto-prefer policies. When an admin clicks "Fetch Models" on the Providers page it requests the fixed official catalog, keeps only normalized valid IDs ending in `-free`, and persists the last successful snapshot. Every saved ID remains an exact raw pin; suffix removal attaches it to an Alias only when that Alias is authorized by the original Go table. Refresh failures or empty results do not overwrite the old snapshot. Turn the card off when Free is not needed; when enabled it is selected along with other accounts by card order. Protocol probe controls are also on the Providers page, not the account card. Zen Free and Go use independent `cooldown_free_until`; Zen Free quotas are shared by egress IP, after a 429 the entire Free channel cools down without swapping Keys, and routing continues trying subsequent compatible cards, returning shared cooldown only when only Free candidates remain. Zen Free inference `401` is returned as-is. OpenCode Go rotates and persists `auth_error` only when the bounded JSON body has exact `/error/type == "CreditsError"`; `ModelError`, unknown, malformed, truncated, or unreadable 401 responses remain passthrough. Re-saving the same Key clears the breaker. Dashboard Ping / Key verification 401s still record `auth_error`. Free channel success rows record `cost_state=free` and do not count against Go quotas. Go's `ox-alpha-free` is still handled by Go's static mapping and counts as `unpriced`, not Free.

## Ollama Cloud

- The family is sealed and fixed-origin: `https://ollama.com`, Chat Completions only, Bearer, no redirects, `ProcessWideNoRedirect` proxy semantics (direction default leg; family model ids never join the per-model exception list). Protocol facts live in the family-independent seed in `ocg_domain::protocol` (`OLLAMA_CLOUD_*`); `MODEL_PROTOCOLS` must stay free of Ollama-only ids because it derives Go's published aliases. The adapter marks `WireNormalization::OllamaCloud`; the forwarder rewrites request bytes per attempt (assistant `reasoning_content` → `reasoning` when missing, `max_tokens`/`max_completion_tokens` clamped to 65535) and normalizes response/SSE frames (`reasoning`/`thinking` → `reasoning_content` backfill). Non-Ollama attempts in a mixed candidate chain must see byte-for-byte identical request bytes; `upstream_body_bytes` logs the bytes actually sent; client-facing attribution keeps the requested name.
- Cookie usage is opt-in and manual-only: the stored web-session Cookie (same obfuscation facility as Keys, never AEAD) is used solely to fetch the exact `https://ollama.com/settings` page (no redirects, 15s timeout, 512KB cap, process-wide outbound default leg). Parsing anchors on `data-usage-track`/`data-usage-segment`/`data-model`/`data-requests`/`data-time`/`data-usage-window` plus the track's `aria-label` (the live page uses bare `data-usage-track` with `aria-label="Session|Weekly usage N% used"`, a sibling `data-time` reset stamp, and per-model `data-usage-segment` buttons); snapshots persist sanitized JSON only, failures update status/backoff without touching the last success, and `unauthorized` marks an expired session. Manual refresh throttles at 30s (success or failure) with fixed 5m → 15m → 1h → 6h backoff; **any usage-path failure never writes inference cooldown, never changes account enablement, and never affects routing eligibility**. State lives in `ollama_cloud_usage_state` (schema v35, cascades with the account). Cookies and usage snapshots are excluded from export payloads; the payload structure and version do not change.

## Usage Sync

- Quota for completed accounts: the official `https://opencode.ai/zen/go/v1/usage` (`go_usage.rs`) is the periodic calibration baseline; local `forward_logs` still do real-time estimation after the last successful calibration. `usage_sync.rs` coordinates manual and background paths: ready+enabled accounts with local activity in the last ~24h reconcile about hourly, inactive ones about daily; disabled/not-ready/empty-Key accounts are not auto-refreshed. Global concurrency 1, with jitter and injectable clock/jitter/fetch seams; no startup thundering herd. Manual `POST /dashboard/api/v3/accounts/{id}/usage/refresh` is still available; server-side throttling is 15s per account (success or failure counts), with concurrent deduplication, returning Retry-After / `next_allowed_at`; failures keep the last baseline and last-success. When local maximum Go usage ≥80%, accelerate reconciliation at most once every 15 minutes. Real inference 429s still write the existing cooldown/selector and additionally schedule an official reconciliation ~1–2 minutes later (not inline); official failures or `status=rate-limited` never write inference cooldown. After success, reschedule by earliest `resetsAt` (plus bounded jitter) respecting active/inactive cadence. Failure backoff: 5m → 15m → 1h → 6h. Sync metadata lives in `provider_usage_sync_state` (`accounts.usage_sync_*` is no longer used). Shared implementation includes CAS / three-window atomic calibration and global proxy. The public Go docs have not listed this endpoint. Do not introduce CDP automation for refresh.

## Pricing, Container, And CI Notes

- Pricing is Provider-scoped: read `GET /dashboard/api/v3/providers/{provider_id}/{offering_id}/pricing`, refresh `POST /dashboard/api/v3/providers/{provider_id}/pricing/refresh`, and write applied multipliers with `PUT /dashboard/api/v3/providers/{provider_id}/{offering_id}/pricing/multipliers`. Go and GOAT multiplier writes are CAS-scoped to their own pricing revision; GOAT writes append a provider snapshot and affect only later request estimates. A refresh must surface multiplier differences before replacing local edits. OpenCode and Command Code use independent revisions and last-good snapshots. Each fixed official source is fetched only when the user clicks that Provider's refresh control; pricing must not auto-poll.
- After a public GitHub Release is published, `.github/workflows/container.yml` builds `linux/amd64` and `linux/arm64` images on native amd64 (`ubuntu-24.04`) and arm64 (`ubuntu-24.04-arm`) runners (smoke-tested on amd64 only), pushes each architecture by digest, then merges them into a single multi-arch OCI index under the same tag, published to `ghcr.io/klarkxy/opencode-go-mgr`. Compose uses this image by default; local source builds need `OCG_IMAGE=ocg-manager:local` then `docker compose up -d --build`.
- `.github/workflows/quality.yml` splits into three parallel jobs on PR / `main`: Web (includes `pnpm run contract:v3:check`, frontend tests/types/lint), Linux workspace Rust tests/Clippy (excluding the Tauri desktop crate; no system packages needed), and Windows Tauri-targeted tests (stubs `dist/`, does not run Vite). `release.yml` invokes the gate only for a production `v*` tag push. A `release.yml` manual candidate (even when a tag ref is selected) is always unsigned and may build only the selected platform; only a `v*` tag push event builds all three platforms and reads repository signing secrets. A tag push is treated as single-maintainer explicit release authorization: the workflow validates that the attachment set matches assembled artifacts name-by-name (quantity derived from artifacts, not hard-coded), updater signature, public-key continuity, and GitHub server-side digest, then automatically publishes the same unchanged draft.
- Container runs fixed as UID/GID `10001` and includes `LICENSE`; Compose passes through optional `OCG_MANAGER_ENCRYPTION_KEY` to support explicit key recovery, but normal deployments still prefer keeping `.encryption-key` in the volume.
